# Детекция трафика сервисов автоматизированного сбора данных

Решение задачи: по событиям суточного окна присвоить каждой `cookie_id` оценку от 0 до 1.
Метрика — **P@R>=0.7**: максимальный precision среди порогов, где recall не ниже 0.70.

| | P@R>=0.7 (OOF) |
|---|---|
| Константа (доля ботов в train) | 0.081 |
| Baseline: 2 признака + RandomForest | 0.111 |
| Только поведенческие признаки | 0.798 |
| Все признаки, кроме построенных на метках прошлых дней | 0.797 |
| **Финальная модель: blend LightGBM + XGBoost + CatBoost** | **0.8875** |

Все числа пересчитываются при запуске `solution.ipynb`; notebook сохранён вместе с выводом.

## Что в папке

```

data/              выданный датасет: train.csv, test.csv, events.csv.gz
submission.csv     предсказания для data/test.csv, получены этим notebook
models/            веса девяти обученных бустингов + список признаков
requirements.txt   версии библиотек, Python 3.12.3
README.md          этот файл
```

Notebook самодостаточен: весь код внутри, внешних модулей нет.

### Сохранённые веса

В `models/` лежат веса всех девяти моделей финального blend'а (3 библиотеки × 3 seed'а)
в нативных форматах — `lgb_seed*.txt`, `xgb_seed*.ubj`, `cat_seed*.cbm` — а не в
`pickle`: нативные форматы переносимы между версиями библиотек и не зависят от версии
Python и scikit-learn.

Рядом:

* `feature_columns.json` — упорядоченный список признаков, на которых модели обучены
  (без него веса применить нельзя: порядок колонок должен совпадать);
* `model_card.json` — гиперпараметры, seed'ы, размер обучающей выборки, схема blend'а.

Если `models/` не пуста, notebook при повторном запуске не переобучает модели, а берёт
веса оттуда. Поэтому при смене версий библиотек папку `models/` нужно удалить — тогда
модели обучатся заново на том же наборе признаков.

Раздел 11 notebook'а содержит функцию `score_from_saved_models(X)`: полный inference
из этой папки без обучения. Там же проверка, что она побитово воспроизводит
`submission.csv`. Предсказание теста в notebook считается **всегда с диска** —
модель обучается, сохраняется, загружается обратно и предсказывает уже загруженная
копия, поэтому сохранённые веса гарантированно полноценны.

## Как запустить

```bash
pip install -r requirements.txt
jupyter lab solution.ipynb      # Run All
```

Полный прогон с нуля — около 30 минут на 8 ядрах: сборка признаков занимает минуту,
остальное — обучение. Матрицы признаков кэшируются в `cache/`, а веса финальных
моделей — в `models/`, поэтому повторный запуск занимает около 10 минут (заново
считается только ablation-таблица раздела 7). Чтобы пересобрать всё с нуля, достаточно
удалить `cache/` и `models/`.

Вся случайность зафиксирована: `SEED = 42` для разбиений, `[11, 22, 33]` для
бустингов — результат воспроизводится побитово.

## Подход

Готовых поведенческих признаков в задаче нет, поэтому решение — это в первую очередь
feature engineering: **379 признаков в четырёх блоках**, после отбраковки по drift
остаётся 357. Дальше три градиентных бустинга с разным индуктивным смещением, каждый
на трёх seed'ах, предсказания усредняются по рангам с равными весами.

### Ключевая идея: что вообще известно на момент конца окна

Окно у каждой куки — ровно сутки, выровненные по полуночи. Значит на момент
`window_end_ts` доступны не только собственные события куки, но и **все события чужих
кук того же дня**, и **вся разметка предыдущих дней**. Отсюда два самых сильных блока
признаков:

* **co-visitation** — несколько кук одного сервиса за сутки обходят один пул объявлений;
* **label propagation** — объявление, которое в прошлые дни уже трогали известные боты,
  компрометирует того, кто смотрит его сегодня.

Вместе они дают скачок с 0.80 до 0.89, причём по ablation в разделе 7.3 notebook'а
видно, что почти весь прирост приходится на label propagation (+0.09). Co-visitation
измеряет ту же связь без меток, и в присутствии меток отдельного вклада уже не даёт —
но он остаётся единственным способом эту связь использовать, если свежей разметки нет.

Чтобы train-часть не подсматривала собственную метку, для куки дня `D` берутся метки
всех размеченных дней **кроме `D`** (leave-one-day-out); для теста — все 14 дней
train, что даёт ту же силу признака.

### Блоки признаков

| Блок | Признаков | О чём | Примеры |
|---|---|---|---|
| `behavior` | 263 | ритм событий, курсор, глубина выдачи, концентрация по рубрикам и городам, User-Agent, воронка контактов | `dt_share_le30`, `ptr_dist_mean`, `page_max`, `loc_per_cat`, `ratio_contact_per_view` |
| `timing` | 67 | интервалы внутри сессии, co-visitation дня, label propagation по прошлым дням | `dti_std`, `cov_inter_sum_norm`, `lp_hit_share`, `te_user_agent_mean` |
| `cookie` | 16 | возраст куки и пакетное создание кук очередями | `cookie_age_days`, `created_nb_600s` |
| `sequence` | 33 | log-likelihood ratio цепочки событий, плотность выкачивания каталога, метки по редким объявлениям | `llr_bi_mean`, `qcov_pages_max`, `lpr_ratio_mean` |

Сильнейшие одиночные признаки — курсорные (|ROC-AUC − 0.5| до 0.44): эмулятор мыши
двигается короткими шагами внутри маленького прямоугольника. Но они покрывают только
36% кук (`pointer_x/y` заполнены лишь для `desktop`/`web`), поэтому итог решают не они,
а связи между куками.

### Обработка данных: три вещи, которые пришлось заметить

1. **Post-window события — data leakage.** В `events.csv.gz` лежат 40 779 событий позже
   `window_end_ts`, и **все они у train-кук**: в тесте таких нет. У ботов их в среднем 22,
   у людей 2. Сюда же попала вся капча целиком (7 928 событий `captcha_shown`): внутри
   окна её ноль. Фильтр по окну стоит на входе pipeline, `captcha_shown` отсеивается
   как константа.
2. **Drift между train и test.** «Возраст объявления в корпусе» и накопленная
   популярность кодируют, сколько дней истории успело накопиться, — а у теста её
   больше, чем у ранних дней train. Такие признаки выбрасываются автоматическим
   фильтром по ROC-AUC разделения train/test.
3. **Пропуски не заполняются.** «Курсора нет вообще» (мобильная кука) и «курсор в углу
   экрана» — разные состояния; у бустингов `NaN` уходит в отдельную ветку дерева.
   Категориальные поля не кодируются напрямую, а сворачиваются в доли, энтропии и
   сглаженные target encoding по прошлым дням.

### Как валидировались

**GroupKFold по календарным дням** — fold забирает дни целиком, иначе внутридневная
co-visitation протечёт из обучения в валидацию. Каждое сравнение усредняется по
нескольким раскладкам дней: bootstrap-интервал метрики на 899 позитивах — ширины
0.043 при 90% доверии, то есть одиночный замер не различает конфигурации, отличающиеся
меньше чем на ~0.02.

Контрольная схема — **forward chaining**: обучение строго на прошлых днях, проверка на
последующих. Она повторяет боевой сценарий и подтверждает результат дневной
кросс-валидации.

### Что пробовалось и не дало прироста

Порядок строк в файле событий, дубликаты событий, секунды таймстампа и их кратность,
почасовые доли по отдельности, флаги `curl` / `Scrapy` / `Headless` в чистом виде,
графовые признаки и KNN по поведению, подбор весов blend вместо равных, отдельный блок
реляционных признаков поверх уже имеющейся co-visitation.

## Ограничения

**Качество резко неоднородно по сегментам.** Половина ботов живёт там, где данных
физически не хватает: мобильная кука не отдаёт координат курсора, а кука с пятью
событиями не отдаёт ритма. Достигнутое в каждом сегменте вплотную к оценке потолка —
расти можно только новыми признаками, не настройкой модели.

**Зависимость от устойчивости пула объявлений.** Label propagation даёт около +0.09 и
предполагает, что сервисы продолжают обходить тот же пул. За наблюдаемый период это
проверено (lift 5.6× без затухания за 11 дней), но при смене целей парсинга блок
деградирует и решение откатится примерно к 0.80. Это самое серьёзное ограничение: одна
идея отвечает за 0.09 из 0.89, поэтому модель требует регулярного переобучения на
свежей разметке.

**Узкая рабочая точка.** При пороге отмечается 710 кук, из них 80 ложных
срабатываний. Чтобы поднять precision на 0.01, нужно убрать всего 8 из этих 80,
поэтому реальный разброс метрики на скрытом тесте — порядка ±0.02, и сравнивать
попытки по третьему знаку бессмысленно.
